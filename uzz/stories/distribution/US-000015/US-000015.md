## distribution/US-000015 — Ship Project Type Profiles in the Knowledge Base Content

### User Story

```
AS A Developer
I WANT common coding standard and development framework basics, per project type, shipped with the Uzzo knowledge base content
SO THAT tools initializing a knowledge base can start a project from sensible content instead of an empty template, and the content evolves with the workflow rather than with each tool
```

#### Technical Context & Constraints
* **Target System**: `uzzo-workflow-kb` artifact, consumed by `nb-uzzo-workflow` and by the `uzzo-init` skill.
* **Toolchain / Rules**: Java 21, Maven, JUnit 5, AssertJ; coding standard `uzz/project/coding_standard.md`.

#### Notes
1. Profiles are plain markdown files under `src/main/uzz/skills/uzzo-init/references/profiles/`, one per project type, shipped by the `uzzo-workflow-kb` artifact like the rest of the content (consumers list them from the jar or folder, as in US-000014).
2. Each profile has two parts: a *match* part (packaging, dependencies, plugins that identify the type) and a *content* part holding the statements that fill the placeholders of `project/coding_standard.md` and `project/development_framework.md` (technology stack, test tools, workflow, build and test commands, language and testing conventions). The exact layout is documented in `skills/uzzo-init/references/profiles/README.md` so that humans, the `uzzo-init` skill and tools read it the same way.
3. A profile states only what is true for every project of that type; anything project specific stays a bracketed placeholder.
4. Initial profiles: a generic Maven Java library (JUnit 5, AssertJ, `mvn clean install` / `mvn test`) and a NetBeans Platform module. More are added by adding files, without code changes in the consumers.
5. Updating the profiles reaches a consumer only when it depends on the new `uzzo-workflow-kb` version; the content is bundled at consumer build time, not fetched at run time.
6. The `uzzo-init` skill is updated to use the profiles when it infers the project type, so both initialization paths propose the same basics.

### Acceptance Criteria

```gherkin
Scenario: Profiles shipped
  Given the project is built
  Then  "uzz/skills/uzzo-init/references/profiles/" files are readable as classpath resources
  And   they are listed with the rest of the content

Scenario: Profile layout documented
  Given the profiles folder
  Then  it contains a README describing the match part and the content part

Scenario: Every profile is well formed
  Given each shipped profile
  Then  it has a non-empty match part
  And   it only fills placeholders that exist in the "coding_standard.md" and "development_framework.md" templates

Scenario: Skill uses the profiles
  Given the "uzzo-init" skill
  When  it infers the project type
  Then  it instructs to pick the matching profile and to leave unmatched facts as placeholders
```
